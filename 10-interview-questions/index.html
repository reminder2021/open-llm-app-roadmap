Python 基础

Python 与异步编程

初级

Q: Python 中 `asyncio` 和多线程有什么区别？为什么 LLM 应用推荐使用异步？

A:

  • 多线程：适合 I/O 密集型任务，但有 GIL 限制，线程切换有开销
  • asyncio：单线程并发，通过事件循环实现，切换开销更小
  • LLM 应用推荐异步：因为大量时间花在等待 API 响应，异步可以在等待时处理其他请求
# 异步调用示例
async def call_llm(prompt: str) -> str:
    async with httpx.AsyncClient() as client:
        response = await client.post("/v1/chat/completions", json={...})
        return response.json()["choices"][0]["message"]["content"]

# 并发调用多个 LLM
results = await asyncio.gather(*[call_llm(p) for p in prompts])

@retry(

LLM 基础

大语言模型原理与使用

初级

Q: 什么是 Temperature？它如何影响模型输出？

A:

  • Temperature 控制输出的随机性，范围通常 0-2
  • 低温度 (0-0.3)：输出更确定、更集中，适合事实性问答
  • 中温度 (0.7)：平衡创造性和准确性
  • 高温度 (1.0+)：输出更多样、更有创意，适合创作

原理：Temperature 缩放 logits，温度越低，概率分布越尖锐，高概率 token 被选中的可能性越大。

Q: 什么是 Token？为什么 LLM 按 Token 计费？

A:

  • Token 是模型处理文本的基本单位，可以理解为"词元"
  • 英文大约 1 token ≈ 4 个字符，中文大约 1-2 个字 = 1 token
  • 按 Token 计费：因为计算量与 token 数量成正比，包括输入和输出

影响：Prompt 越长、输出越长，成本越高。优化 prompt 长度可以降低成本。

中级

Q: 如何确保 LLM 输出符合 JSON Schema？有哪些方案？

A:

  1. Prompt 约束：在提示中明确要求 JSON 格式，提供 schema 示例
  2. 输出解析：使用 Pydantic 或 JSON Schema 校验，失败则重试
  3. Constrained Decoding：vLLM、Outlines 等工具限制输出 token
  4. Function Calling：利用模型的工具调用能力返回结构化数据
from pydantic import BaseModel, ValidationError

class ProductInfo(BaseModel):
    name: str
    price: float
    features: list[str]

def extract_product(text: str, max_retries: int = 3) -> ProductInfo:
    prompt = f"提取产品信息，返回JSON：{ProductInfo.model_json_schema()}\n\n{text}"
    for _ in range(max_retries):
        response = call_llm(prompt)
        try:
            return ProductInfo.model_validate_json(response)
        except ValidationError:
            continue
    raise ValueError("无法提取有效产品信息")
RAG 知识库

检索增强生成

初级

Q: 什么是 RAG？为什么需要 RAG 而不是直接用 LLM？

A:

RAG (Retrieval-Augmented Generation) 是检索增强生成，先检索相关文档，再基于文档生成答案。

为什么需要 RAG：

  • 知识时效：LLM 训练数据有截止日期，RAG 可以使用最新文档
  • 领域知识：LLM 缺少企业私有数据，RAG 可以引入内部知识库
  • 减少幻觉：要求模型基于检索到的事实回答，而非编造
  • 可追溯：答案可以引用来源，便于验证

Q: 文档切分（Chunking）太大或太小各有什么问题？

A:

  • 太小：丢失上下文，模型无法理解完整语义
  • 太大：检索不精确，无关信息多，占用 token 预算
  • 推荐：300-500 tokens，按语义边界切分（段落、章节）

最佳实践：

  • 保留重叠（overlap）以维持上下文连续性
  • 保留 metadata（来源、页码、章节标题）
  • 表格、代码块等结构化内容整体保留

中级

Q: 什么是 Rerank？为什么检索后还需要 Rerank？

A:

Rerank 是对初步检索结果进行重新排序的过程。

为什么需要：

  • 向量检索是近似搜索，可能遗漏最佳结果
  • 初检 Top-K 通常设较大（如 20），需要精选
  • Rerank 模型更精确，考虑 query-document 的交互
# 典型 RAG 流程
1. 用户提问
2. 向量检索 Top-20
3. Rerank 精选 Top-5
4. 将 Top-5 作为上下文生成答案

常用 Rerank 模型：Cohere Rerank、bge-reranker、cross-encoder

Q: 如何评估 RAG 系统的效果？有哪些指标？

A:

检索质量指标：

  • Recall@K：Top-K 结果中包含正确文档的比例
  • MRR：正确文档排名的倒数平均值
  • NDCG：考虑排名位置的评分

生成质量指标：

  • Faithfulness：答案是否忠实于检索到的文档
  • Answer Relevancy：答案是否与问题相关
  • Context Precision：检索到的上下文是否精确

推荐工具：Ragas 框架，可自动化评估 RAG 全链路

高级

Q: 如何处理 RAG 中的"幻觉"问题？

A:

幻觉来源：

  • 检索到了不相关的文档
  • 模型忽略上下文，使用自身知识回答
  • 上下文信息不足，模型"补全"

解决方案：

  1. Prompt 设计：明确要求"只基于上下文回答，没有则说不知道"
  2. 引用机制：要求模型标注答案来源
  3. 检索优化：提高检索精度，使用 Rerank
  4. 后处理：校验答案是否有对应上下文支持
  5. 置信度：返回检索分数，低于阈值时提示不确定性

中级

Q: Function Calling 是如何工作的？如何设计好的工具描述？

A:

Function Calling 流程：

  1. 定义工具 Schema（名称、描述、参数）
  2. 将工具定义和用户问题发送给模型
  3. 模型决定是否调用工具，返回调用参数
  4. 应用层执行工具，将结果返回给模型
  5. 模型基于工具结果生成最终答案

好的工具描述：

tools = [{
    "type": "function",
    "function": {
        "name": "search_documents",
        "description": "在知识库中搜索文档。当用户询问产品信息、技术规格、使用方法时使用。",
        "parameters": {
            "type": "object",
            "properties": {
                "query": {
                    "type": "string",
                    "description": "搜索关键词，建议使用产品名称或功能描述"
                },
                "top_k": {
                    "type": "integer",
                    "description": "返回结果数量，默认5",
                    "default": 5
                }
            },
            "required": ["query"]
        }
    }
}]
微调

模型微调

初级

Q: 什么时候需要微调？什么时候用 RAG 就够了？

A:

用 RAG：

  • 知识会频繁更新
  • 需要引用来源
  • 数据量大（>10万文档）
  • 需要快速上线

用微调：

  • 需要特定风格/格式输出
  • 领域术语多，模型不理解
  • 需要压缩模型规模
  • 任务复杂，Prompt 难以描述

两者结合：微调模型学习领域知识 + RAG 提供最新信息

中级

Q: LoRA 和全量微调有什么区别？各自适用场景？

A:

维度LoRA全量微调
参数量原模型 0.1-1%100%
显存低（7B 约 16GB）高（7B 约 60GB）
效果接近全量最佳
场景资源有限、快速迭代追求极致效果

QLoRA：4-bit 量化 + LoRA，进一步降低显存需求，7B 模型只需 8GB 显存。

评估

评估体系

初级

Q: 为什么 LLM 应用需要专门的评估体系？不能人工评估吗？

A:

人工评估的问题：

  • 成本高、速度慢
  • 主观性强，不同人标准不一
  • 无法频繁执行，阻碍迭代

自动化评估的价值：

  • CI/CD 集成，每次改动自动评估
  • 量化指标，便于对比和追踪
  • 快速发现问题，加速优化

最佳实践：自动化评估为主 + 人工抽检为辅

中级

Q: 如何构建有效的测试集？需要注意什么？

A:

测试集构成：

  • 覆盖度：涵盖各种问题类型（简单/复杂、常见/边缘）
  • 真实性：使用真实用户问题，而非人造
  • 标注质量：Ground Truth 需要专家审核
  • 规模：至少 50-100 条，越多越好

注意事项：

  • 定期更新测试集，避免过拟合
  • 包含"无法回答"的案例
  • 记录评估时间和版本
部署

部署与工程化

初级

Q: LLM 应用部署需要考虑哪些关键因素？

A:

  • 并发处理：LLM 推理慢，需要异步 + 队列
  • 超时控制：设置合理超时，避免请求堆积
  • 成本控制：监控 token 消耗，设置预算告警
  • 缓存策略：相同问题缓存答案，减少调用
  • 日志监控：记录每次调用的输入、输出、耗时
  • 错误处理：优雅降级，返回友好错误信息

中级

Q: 如何估算 GPU 显存需求？选择什么规格的 GPU？

A:

显存估算公式（FP16）：

显存 (GB) ≈ 参数量 (B) × 2

示例：

  • 7B 模型：约 14GB → 推荐 24GB GPU (3090/4090)
  • 13B 模型：约 26GB → 推荐 40GB GPU (A100)
  • 70B 模型：约 140GB → 需要多卡或量化

量化后：

  • INT8：显存减半
  • INT4：显存为 1/4

建议：先用量化版本验证效果，再决定是否需要全精度。

系统设计

综合系统设计题

高级

Q: 设计一个企业级知识库问答系统，需要考虑哪些方面？

A:

需求分析：

  • 用户场景：客户自助查询、客服辅助、内部知识共享
  • 文档类型：PDF、Word、HTML、Markdown
  • 性能要求：响应时间、并发量、可用性

架构设计：

用户 → API Gateway → 负载均衡
                ↓
         RAG 服务集群
         ├── 文档处理服务（解析、切分、索引）
         ├── 检索服务（向量检索 + 关键词检索 + Rerank）
         └── 生成服务（LLM 推理）
                ↓
         存储层
         ├── 向量数据库（Qdrant/Milvus）
         ├── 对象存储（文档原文）
         └── 缓存（Redis）

关键设计点：

  • 权限控制：按部门/角色过滤文档
  • 增量更新：文档变更自动重新索引
  • 监控告警：成功率、延迟、成本监控
  • A/B 测试：对比不同模型/策略效果

Q: 如何设计一个支持多轮对话的 Agent 系统？

A:

核心组件：

  • 对话管理器：维护会话状态、历史消息
  • 规划器：分解任务、决定执行顺序
  • 工具执行器：调用外部工具、处理结果
  • 记忆系统：短期（当前对话）+ 长期（用户偏好）

状态管理：

class AgentState:
    messages: list[dict]      # 对话历史
    current_plan: list[str]   # 当前计划
    tool_results: dict        # 工具执行结果
    context: dict             # 上下文信息
    step: int                 # 当前步骤

关键挑战：

  • 上下文窗口限制：摘要历史、滑动窗口
  • 错误恢复：工具调用失败后的重试/降级
  • 人机协作：何时需要人工确认
